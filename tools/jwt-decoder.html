JWT Decoder

Decode JWT tokens to inspect the header and payload, with expiry checking.

What Is the JWT Decoder?

A JSON Web Token, JWT, is the credential format used by most modern authentication systems: a compact, signed string carrying claims about who you are. It looks opaque, but its first two parts are simply Base64-encoded JSON that anyone can read. This JWT Decoder opens the token up instantly, showing the header, the payload and the expiry status.

Paste a token and the tool decodes the header, which names the signing algorithm, and the payload, which carries the claims: subject, issuer, issued-at and expiry timestamps, and any custom claims your system adds. The expiry is interpreted into a human-readable time with a clear expired or valid indication.

Developers use it to debug authentication failures, to see exactly which claims a system is issuing, and to check expiry maths; security learners use it to internalise the crucial lesson that JWT contents are readable by anyone, and that only the signature, not encoding, protects integrity. The tool runs locally, so tokens are never transmitted.

How to Use the JWT Decoder

Paste the token into the input box and the decoded header and payload appear immediately, formatted as readable JSON. The expiry status line tells you whether the token is currently valid and when it lapses.

  1. Copy the full JWT from your application, request header or storage.
  2. Paste it into the input area.
  3. Read the decoded header to see the algorithm and token type.
  4. Read the payload to see the claims, including subject and issuer.
  5. Check the expiry line to see whether the token is valid and when it expires.

How the JWT Decoder Works

A JWT is three Base64url-encoded segments joined by dots: header, payload and signature. The header is JSON naming the algorithm, typically HS256 or RS256. The payload is JSON containing registered claims such as sub for subject, iss for issuer, iat for issued-at and exp for expiry, expressed as seconds since the Unix epoch, plus any custom claims.

The tool decodes the first two segments with the URL-safe Base64 variant and parses the JSON for display. The third segment, the signature, is deliberately not processed: verifying it requires the secret or public key, and this tool does not ask for keys. Decoding shows what a token says; verification is a separate question answered by your backend.

The expiry claim is compared against your device's current time and shown as valid or expired with the exact lapse time. A frequent debugging discovery is a clock mismatch: a token that looks valid may be expired on a server whose clock differs, or vice versa. Seeing the exact expiry timestamp resolves that class of confusion quickly.

The signature's role deserves a precise description, because decoding a token without understanding it leads to a dangerous misconception. The signature is computed over the header and payload with a secret or private key. Changing one character of the payload invalidates the signature, which is what stops tampering. But nothing about the signature hides the payload: reading requires no key, verifying does. Confidentiality is a separate feature, provided by encrypted token formats when it is actually needed.

Algorithm confusion is the classic JWT vulnerability worth knowing about. Systems that trust the header's algorithm field can be tricked into verifying with the wrong method, accepting a token the attacker signed. The defence lives on the server, pinning the expected algorithm. On the client side, the practical rule is simpler: treat decoded claims as unverified data until the backend has done its job.

Examples and Practical Use Cases

Debugging a 401 error

An API rejects a request as unauthorized. Decoding the token reveals an expiry from yesterday: the client kept using a stale token instead of refreshing. The decoded exp claim turns a mystery into a one-line fix.

Inspecting issued claims

A developer wants to know which roles an identity provider includes in tokens. Decoding a live token lists the exact claim names and values, which is far faster than reading provider documentation.

Teaching token safety

A security instructor pastes a student's token into the decoder, revealing their email and role in plain text. The lesson lands: encoding is not encryption, and tokens must never contain secrets.

Common Mistakes to Avoid

  • Putting sensitive data in a JWT payload because it looks opaque; it is readable by anyone holding the token.
  • Assuming a token is valid because it decodes cleanly; decoding says nothing about the signature.
  • Storing tokens in URLs, where they leak into logs and referrer headers.
  • Ignoring the exp claim and reusing tokens long after they should have been refreshed.

Tips, Benefits and Limitations

  • Never paste production tokens into tools that send data to a server; this one runs locally.
  • The signature is not verified here; decoding shows claims, verification needs the key.
  • Check exp first when a token misbehaves; expiry is the most common failure.
  • Claims are just names; custom claims like roles are only meaningful within your system.
  • Tokens are credentials: decoding one does not make it safe to share the original.

Frequently Asked Questions

Does this tool verify the signature?

No. Verification requires the signing key and belongs on the server. This tool decodes and displays the readable parts, which is exactly what most debugging needs.

Is a JWT encrypted?

Usually not. A standard JWT is only encoded, so anyone holding it can read the claims. Encrypted tokens use the separate JWE format and look similar.

Why does my token contain strange characters instead of JSON?

You may have pasted only part of the token, or the string was altered. A JWT has exactly three dot-separated segments.

What does the exp number mean?

It is seconds since the Unix epoch, the same convention as Unix timestamps. The tool converts it to a readable date and compares it to now.

Can decoding damage or invalidate the token?

No. Decoding is read-only. The token remains valid wherever it is used; nothing about this tool changes it.

Is my token uploaded?

No. Decoding happens entirely in your browser, and the token never leaves your device.

What is the difference between JWT and session cookies?

Sessions store state server-side and hand the client an opaque key. JWTs carry the state inside the token itself, signed so it cannot be altered. Each approach has trade-offs in scale and revocation.

Can I decode a token without the secret?

Yes, that is the point of this tool. The header and payload are encoded, not encrypted. Only signature verification needs the key.
