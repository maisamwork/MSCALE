Base64 Encode / Decode

Encode text to Base64 or decode Base64 to text. UTF-8 safe, runs in your browser.

What Is the Base64 Encode / Decode?

Base64 is a way of representing binary data using only plain text characters, which is why it appears everywhere: email attachments, data URLs that embed images in HTML and CSS, JSON Web Tokens, API payloads that must survive text-only channels. This Base64 Encoder and Decoder converts text to Base64 and back, with full UTF-8 support.

Paste text to encode it into a safe, transmission-friendly string, or paste Base64 to decode it back into readable text. The tool handles the Unicode cases that trip up naive implementations, so names, emoji and non-Latin scripts encode and decode correctly rather than corrupting.

Developers use it for data URLs, basic auth headers and debugging token payloads; email and integration work depends on it constantly; and it is a common interview and learning topic, making the tool a convenient way to build intuition for how the encoding behaves.

How the Base64 Encode / Decode Works

Base64 encodes every 3 bytes of input into 4 characters from a 64-character alphabet of letters, digits, plus and slash, with equals signs as padding when the input is not a multiple of 3 bytes. Every 6 bits of data maps to one alphabet character, which is why encoded output is about a third larger than the input.

The critical detail is UTF-8 handling. Text is first converted from characters to UTF-8 bytes, and those bytes are encoded. Decoding reverses the process. This two-step design is what makes multi-byte characters work: a name like Jose with an accented e, or text in Arabic or Chinese, survives the round trip intact instead of emerging mangled.

Padding equals signs appear at the end when needed, and their presence or absence is itself information about the input length. If a decoded result looks like gibberish, the most common cause is trying to decode text that was never Base64, or Base64 that was modified in transit, for example by a system that replaced the plus and slash characters.

Knowing where Base64 appears in the wild makes the tool's uses concrete. Email attachments ride inside MIME containers as Base64 because email was designed for text. Data URLs embed resources directly in HTML, CSS and JSON. JSON Web Tokens encode their segments with the URL-safe variant. Basic authentication headers are literally the word Basic followed by Base64 of username colon password. Meeting any of these in the wild is a matter of time, and the decoder turns them from opaque strings into readable data.

The size cost has a precise arithmetic worth internalising: every 3 bytes become 4 characters, a 33 percent overhead, plus padding. For embedding small icons in stylesheets this is usually a good trade, one fewer request and no cache complexity. For large images it is a poor one, since the overhead multiplies and the benefit of data URLs disappears. The rule of thumb is small assets inline, large assets as files.

Examples and Practical Use Cases

Embedding an image in CSS

A small logo is encoded and embedded as a data URL, removing one HTTP request. The decoder verifies the encoded string reproduces the original before it is committed to the stylesheet.

Debugging an auth header

A failing API call uses Basic authentication. Decoding the header value shows exactly which username and password string is being sent, revealing a stray space that was causing the 401.

Reading a JWT payload

The middle segment of a JSON Web Token is Base64-encoded JSON. Decoding it reveals the claims inside, which is the first step in debugging almost any token problem.

Common Mistakes to Avoid

  • Treating Base64 as a security measure and shipping sensitive data thinking it is protected.
  • Embedding large files as data URLs and wondering why the page weight ballooned by a third.
  • Copying Base64 with surrounding whitespace or quotes, which breaks decoding.
  • Mixing up standard and URL-safe variants when moving encoded data between systems.

Tips, Benefits and Limitations

  • Base64 is encoding, not encryption; anyone can decode it, so never treat it as protection.
  • Output is about a third larger than the input, which matters for size budgets.
  • Round-trip check: encode then decode, and confirm you get the original back.
  • Some systems use URL-safe Base64 with minus and underscore; those variants will not decode here unchanged.
  • Gibberish on decode usually means the input was not valid Base64 to begin with.

Frequently Asked Questions

Is Base64 encryption?

No. It is a reversible encoding with no secret. Anyone can decode it. Use it for transport compatibility, never for confidentiality.

Why is the encoded text longer than the input?

Base64 packs 3 bytes into 4 characters, so output is about 33 percent larger, plus padding. That is the cost of representing binary data in a text-safe alphabet.

Does it support emoji and non-Latin text?

Yes. The tool converts text to UTF-8 bytes before encoding, so all Unicode characters round-trip correctly.

What are the equals signs at the end?

Padding. They make the encoded length a multiple of 4 and encode information about the input's length. They are part of standard Base64.

Why does decoding produce strange characters?

The input was probably not valid Base64, or it was altered, for example by URL-encoding the plus and slash characters. Verify the source of the string.

Is my data sent anywhere?

No. Encoding and decoding happen entirely in your browser.

What is URL-safe Base64?

A variant that replaces the plus and slash characters with minus and underscore so the output can appear in URLs without escaping. If decoding fails, check whether your input uses this variant.

Why do some Base64 strings have no padding?

Some systems strip the trailing equals signs to save space and re-add it implicitly. This tool accepts unpadded input for decoding in most cases.
